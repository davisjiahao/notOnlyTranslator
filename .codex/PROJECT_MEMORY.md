## 2026-08-03 翻译集成可靠性修复

### 决策记录
- 为什么按供应商响应类型分流而非统一解析：传统翻译 API 返回纯文本，LLM 返回结构化 JSON；在服务边界分流可保留 LLM 批处理能力，同时避免传统响应被错误解析。
- 为什么以活动配置作为唯一路由来源：非活动配置只用于备用，不应改变当前供应商、DeepL 专用路径或双密钥签名。
- 为什么在设置页申请自定义端点权限：`chrome.permissions.request` 需要用户手势，自动翻译阶段不具备可靠的授权时机。

### 可复用模式
- 消息边界运行时校验：在后台路由入口验证批量 payload，再进入持久化和业务服务 → `src/background/index.ts`
- 供应商能力分流：通过 `apiFormat` 区分纯文本翻译与结构化 LLM 翻译 → `src/background/translation.ts`、`src/background/batchTranslation.ts`
- 活动配置覆盖：读取设置时统一应用活动配置的 provider、URL、模型和次级密钥 → `src/background/storage.ts`
- 单配置自动激活：缺少活动 ID 时回填首个配置 ID，保证后续凭证读取使用同一配置 → `src/background/storage.ts`

### 避坑指南
- 问题：TypeScript 类型断言不会校验 Chrome 消息的运行时数据，错误 payload 会在深层调用中抛出难定位异常。
- 解决：在消息入口验证对象、数组、必填字符串及枚举字段，失败时返回稳定错误。
- 预防：每个新增消息入口同时增加发送端结构测试和接收端异常负载测试。

- 问题：用“任意已保存配置”判断供应商能力会让非活动 DeepL 或 API Key 污染当前路由。
- 解决：只读取活动配置，旧版顶层字段仅作为无配置时的兼容回退。
- 预防：多配置功能的测试必须同时覆盖活动配置和非活动配置并存场景。

- 问题：传统翻译响应被送入 LLM JSON 解析器，导致成功的 API 响应仍被判定失败。
- 解决：按 `apiFormat` 调用纯文本翻译方法并包装为统一 `TranslationResult`。
- 预防：新增供应商时明确声明认证要求、响应类型和是否支持批量结构化输出。
