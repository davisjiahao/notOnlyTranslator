# 竞品分析：notOnlyTranslator vs 沉浸式翻译 (Immersive Translation)

> 分析日期：2026-05-13  
> 分析范围：代码架构、UI/UX、功能矩阵、翻译性能、LLM 模型选型  
> 主竞品：沉浸式翻译 v1.29.3（最新版）  

---

## 一、执行摘要

notOnlyTranslator 与沉浸式翻译在**产品定位上有本质区别**，并非直接竞争关系，而是互补定位：

| 维度 | notOnlyTranslator | 沉浸式翻译 |
|------|------------------|-----------|
| **定位** | 分级英语学习翻译工具 | 全能双语网页翻译工具 |
| **用户需求** | "帮我学英语，只翻译我不会的词" | "帮我把所有内容译成中文" |
| **核心差异化** | 词汇级自适应翻译（按用户水平过滤） | 竖排双语对照 + 多引擎生态 |
| **用户量级** | 未公开 | 1000万+ |
| **开源** | ✅ 完全开源 | ❌ 非开源（旧版2023年归档） |

**核心结论**：不应以功能完整性对标沉浸式翻译，而应强化"按学习者词汇水平自适应翻译"这一垂直差异化优势。

### 关键发现
- **功能完整性上沉浸式翻译大幅领先**（10+ 年积累、全职团队、1000万用户驱动）
- **英语学习场景功能我们全面领先**（分级翻译、掌握度追踪、间隔重复、语法分析）
- 沉浸式翻译本质是"翻译工具"，我们是"英语学习工具"——产品形态不同

## 四、翻译性能深度对比

### 4.1 性能关键指标

| 指标 | notOnlyTranslator | 沉浸式翻译 |
|-----|------------------|-----------|
| 扫描机制 | IntersectionObserver + 1200px预加载 | 闭源 |
| 渲染优化 | RAF 分帧 (10节点/帧, 16ms/帧) | 闭源 |
| 批量翻译 | 并发5批, LIFO优先新段落 | 闭源 |
| 防抖延迟 | 150ms | 闭源 |
| 虚拟滚动 | ✅ (200px 预渲染) | 闭源 |
| 离线段落取消 | ✅ | 闭源 |
| 中文页面跳过 | ✅ (30% 中文阈值) | 闭源（整页翻译，无此逻辑） |

### 4.2 差异化性能策略

**notOnlyTranslator 独有的优化**：
- **本地词频过滤**：在调用 API 之前使用 `frequencyManager` 判断段落是否包含超纲词，简单段落直接跳过 API 调用。这是分级翻译模式的独特优势——不需要每次都调用 LLM。
- **三级缓存**：内存 LRU (500条) → Chrome Local Storage (1000条) → DOM data-attrs 层

**沉浸式翻译的优势**：
- 传统翻译引擎（Google/MS Translate）延迟极低，无需等待 LLM 推理
- 20+ 引擎可以并行或智能路由到最快的引擎

### 4.3 延迟估算对比

| 场景 | notOnlyTranslator | 沉浸式翻译 |
|------|:-----------------:|:----------:|
| 简单段落（不含超纲词） | **~200ms** (本地判断+跳过) | ~500ms (调用引擎) |
| 含生词的段落 (LLM) | ~2-5s (API调用) | N/A (不按词汇过滤) |
| 含生词的段落 (DeepL) | ~500ms | ~300ms |
| 整页翻译 | ~5-15s (分批LLM) | ~1-3s (传统引擎) |

### 6.2 推荐默认引擎策略

基于浏览器翻译扩展场景（短文本、实时性、成本敏感），推荐以下分层策略：

```
免费用户默认：
  → Gemini 2.0 Flash 或 GPT-4o-mini（成本最低, 质量足够）
  → 回退: Google Translate（零成本）
  
付费/高精度场景：
  → 质量优先: Claude Sonnet 4.6 或 GPT-4o
  → 速度优先: DeepL（无需 LLM 推理延迟）
  
混合模式（推荐发展方向）：
  → 简单句子: DeepL（快速, 低成本）
  → 含生词段落: GPT-4o-mini（需要分级分析）
  → 复杂长句: Claude Sonnet（需要深度理解）
```

### 6.3 关键洞察

1. **GPT-4o-mini 是当前英译中性价比之王**：价格为 GPT-4o 的 1/17，质量达到 90-95%。对于浏览器扩展场景（段落级翻译）完全足够。

2. **Gemini Flash 系列延迟最低**：适合对速度敏感的实时翻译场景，但中文翻译质量略低于 GPT-4o-mini 和 Haiku。

3. **DeepL 在传统翻译引擎中仍有不可替代性**：无需 prompt 设计、字符计费直观、延迟极低、质量优秀。适合作为混合翻译策略中的 "简单文本处理器"。

4. **本地模型 (Ollama) 是隐私敏感用户的唯一选择**：Qwen 2.5 7B 的中文能力在 7B 级别开源模型中表现最佳。

## 七、notOnlyTranslator 现存差距与改进方向

### 7.1 需紧急修复的差距

| 差距 | 影响 | 建议优先级 |
|-----|------|:---------:|
| API 配置引导不够流畅 | 新用户上手门槛高 | P0 |
| 缺乏免费翻译引擎回退 | 无 API Key 用户完全不可用 | P1 |
| 不支持浏览器右键菜单翻译 | 用户习惯不符合 | P1 |

### 7.2 可选择性增强的功能

| 功能 | 价值 | 实现成本 | 建议 |
|-----|:----:|:-------:|:----:|
| 输入框翻译 | 中 | 中 | P2：常见需求 |
| 浏览器弹出式翻译（非面板） | 中 | 低 | P2：QuickActions 已有基础 |
| PDF 阅读模式 | 低 | 高 | P3：与核心定位偏离 |
| 更多传统翻译引擎接入 | 高 | 中 | P1：Google/MS Translate 免费引擎 |

### 7.3 绝对不应做的事

- ❌ 做片翻译（沉浸式翻译已做到极致）
- ❌ 做视频字幕翻译（工程复杂度极高）
- ❌ 做会议实时翻译（需要实时音频处理）
- ❌ 做漫画/图片翻译（与英语学习定位无关）

## 八、战略建议

### 8.1 核心差异化强化

**我们应该加倍投入的（"矛"）：**

1. **分级翻译算法优化** — 当前基于 LLM prompt 的分级策略可以更精准。考虑加入：
   - 本地 CEFR 词表匹配（高频词跳过，减少 API 调用）
   - 词频统计 + LLM 分析的混合判断
   - 用户标记反馈闭环（标记已知 → 自动降级难度）

2. **学习闭环完善** — 沉浸式翻译完全不涉及的领域：
   - 阅读中遇到生词 → 一键加入复习队列
   - 根据阅读内容自动生成词汇练习
   - 学习进度可视化（词汇量增长趋势）

3. **零成本入门体验** — 沉浸式翻译的用户基数壁垒是 1000 万 vs 我们的核心差距：
   - 内置 Google Translate 免费引擎作为基础设施
   - API Key 非必要（使用免费引擎即可体验核心分级翻译）
   - 引导用户从免费版 → 自备 API Key → 付费订阅

### 8.2 需要弥补的短板（"盾"）：

1. **浏览器覆盖** — 当前仅 Chrome/Edge，需考虑 Firefox（扩展市场第二）
2. **免费引擎接入** — 这是最大硬伤，用户需要 API Key 才能使用
3. **右键菜单翻译** — 最基本的浏览器扩展交互模式

### 8.3 路线图优先级

```
P0 (立即): 
  - 接入 Google Translate 作为默认免费引擎
  - 优化 API 配置体验（WelcomeModal 已存在，需强化）
  
P1 (本月):
  - 右键菜单翻译
  - 本地 CEFR 词表过滤（减少 50%+ API 调用）
  - 学习数据看板（词汇量增长趋势）
  
P2 (下月):
  - 输入框翻译
  - Firefox 版本
  - 阅读复习闭环（遇到→标记→复习→掌握）
  
P3 (远期):
  - 多设备同步（Chrome sync 已有基础）
  - 社区共享词表/提示词模板
```

## 九、附：沉浸式翻译的"可学习之处"

| 做法 | 为何值得学习 |
|-----|------------|
| **引擎生态开放** | 不是绑定一个引擎，而是开放生态让用户自选。降低选择门槛 + 提高可靠性 |
| **快速迭代节奏** | 每月 3-5 次更新，持续改善。我们的迭代频率需要提升 |
| **多平台覆盖** | Chrome/Firefox/Safari/Mobile 全覆盖，用户在哪扩展就在哪 |
| **快捷键驱动交互** | 三击空格、Ctrl+悬停，比点击扩展图标更高效 |
| **先发制人的文档翻译** | PDF/EPUB/DOCX 全覆盖，虽然这不是我们的核心方向，但说明了功能扩展的思路 |
