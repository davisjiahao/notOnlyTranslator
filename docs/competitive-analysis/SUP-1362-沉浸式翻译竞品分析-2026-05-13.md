# 竞品分析：notOnlyTranslator vs 沉浸式翻译 (Immersive Translate)

> 分析日期: 2026-05-13
> 分析人: Product Manager
> 状态: 已完成

## 一、产品定位对比

| 维度 | notOnlyTranslator | 沉浸式翻译 |
|------|------------------|-----------|
| **核心定位** | 按学习者词汇水平**自适应翻译**的英语学习工具 | 支持多语言的**沉浸式双向翻译**工具 |
| **目标用户** | 英语学习者（CET-4/6、TOEFL、IELTS、GRE 备考者） | 普通阅读者、跨境工作者、内容创作者 |
| **差异化价值** | 只翻译超出用户词汇水平的内容，帮助边读边学 | 支持几乎所有网站的双语对照翻译，覆盖广 |
| **亮点功能** | 自适应词汇分级、语法点分析、单词掌握度追踪、间隔复习 | PDF 翻译、视频双语字幕、鼠标悬停翻译、输入框翻译 |
| **开源** | 否 | 否（GitHub 仅发布二进制，旧版代码 2023 年已归档） |

## 二、翻译引擎对比

### 2.1 notOnlyTranslator 翻译引擎

**支持的翻译供应商（12种）：**

| 供应商 | 默认模型 | 格式 | 用途 |
|--------|---------|------|------|
| OpenAI | GPT-4o Mini | chat | 主 LLM 翻译 |
| Anthropic | Claude 3.5 Haiku | anthropic | 备选 LLM |
| Google Gemini | Gemini 2.0 Flash | gemini | 备选 LLM |
| Groq | Llama 3.3 70B | openai | 超快推理 |
| DeepSeek | DeepSeek Chat | openai | 国产，性价比高 |
| 智谱 AI | GLM-4 Flash | openai | 国产 |
| 阿里通义 | Qwen Turbo | dashscope | 国产 |
| 百度文心 | ERNIE Speed | baidu | 国产 |
| Ollama | Qwen 2.5 7B | ollama | 本地部署 |
| **DeepL** | DeepL Free | deepl | 专业翻译 |
| **Google Translate** | 标准 API | google_translate | 传统翻译 |
| **有道翻译** | 标准版 | youdao_translate | 国产翻译 |
| **自定义 API** | 可配置 | openai | 任意兼容端点 |

**混合翻译策略（核心创新）：**
- 基于文本复杂度（TextComplexityAnalyzer）智能路由
  - 简单文本 → 传统API（DeepL/有道/Google Translate）
  - 中等文本 → 混合模式（传统 + LLM 增强分析）
  - 复杂文本 → LLM（完整 JSON 解析）
- 并行翻译模式：同时请求传统API和LLM，取最快结果
- 多层次错误回退：traditional → llm → simple（原文回退）
- LLM 增强分析：为生词提供音标、词性、例句

**缓存策略（多层缓存体系）：**
- **增强缓存**（EnhancedCacheManager）：内存 LRU（500条，双向链表 O(1) 淘汰）+ Chrome Storage 持久化（防抖 1s）
  - DeepL 结果缓存 30 天，混合翻译缓存 14 天，LLM 结果缓存 7 天
  - 达到 95% 容量时提前淘汰最早 10%
- **旧版缓存**：独立 translationCache，上限 1000 条
- **批量翻译缓存**：段落级别缓存
- **百度 OAuth token 缓存**：内存缓存，提前 5 分钟过期

### 2.2 沉浸式翻译翻译引擎

沉浸式翻译主要采用：
- **20+ 翻译引擎**（业内最多），包括：Google Translate、OpenAI(ChatGPT)、Gemini、DeepL、Microsoft Translator、DeepSeek、Claude、Grok、Ollama、OpenRouter、Qwen-MT、智谱GLM、百度翻译、腾讯混元、字节火山引擎、有道翻译、小牛翻译、彩云小译、OpenL、SiliconFlow等
- 翻译服务聚合：多个翻译源同时查询，取最佳结果
- 内置翻译质量评分系统
- AI 增强模式：用 LLM 对传统翻译结果进行质量改进
- **5 种提示词类型**：系统提示词、用户提示词、多段落系统提示词、多段落用户提示词、字幕提示词
- 提示词支持变量（`{{text}}`、`{{from}}`、`{{to}}`、`{{content_type}}`、`{{title_prompt}}`、`{{terms_prompt}}`等）
- AI 术语库（Pro功能）和用户自定义术语表

**核心差异：** 沉浸式翻译支持更多传统翻译服务（微软翻译、Amazon Translate、彩云小译等），提示词体系比 notOnlyTranslator 更灵活（支持更多变量和 YAML 自定义流程）。但不具备自适应词汇分级的提示词工程，也没有 A/B 测试或版本管理能力。

### 2.3 提示词工程对比

**notOnlyTranslator 的提示词体系（独特优势）：**

notOnlyTranslator 拥有行业领先的翻译提示词工程体系：

- **TranslationPromptBuilder**：基于用户词汇量、考试类型、功能开关动态构建提示词
- **PromptVersionManager**：支持多个提示词版本（v1.0.0 默认，v2.0.0-beta 实验版）
- **A/B 测试框架**：内置 promptEvaluator + ABTestFramework，支持版本对比
- **测试用例管理**：STANDARD_TEST_CASES 覆盖不同难度和领域
- **输出 Schema 定义**：严格的 JSON Schema 确保 LLM 输出的解析稳定性
- **评估框架**：QualityEvaluator 自动评估翻译质量

**沉浸式翻译：**
- 使用预定义翻译提示词
- 不支持多版本管理或 A/B 测试
- 不支持输出格式强制（无 JSON Schema 校验）

**差距分析：** notOnlyTranslator 的提示词管理能力远胜沉浸式翻译，这是由于其"自适应分级"的核心需求决定的。

### 2.4 核心翻译流程差异

**notOnlyTranslator 三段式翻译策略：**
1. **传统 API 优先**（DeepL/Google/有道）→ 快！<500ms
2. **混合模式** → 传统 + LLM 异步增强词汇/语法分析
3. **LLM 完整翻译** → 解析 JSON 含词汇、短语、语法点、全文翻译

**沉浸式翻译策略：**
1. 选定翻译服务（可为单个或多个）
2. 发起翻译请求
3. 直接展示译文（流式或一次性）

**差异本质：** notOnlyTranslator 的 LLM 调用更重（每次返回完整 JSON 分析），但带来更多教育价值；沉浸式翻译更轻，更适合快速阅读。

### 3.2 翻译模式对比

**notOnlyTranslator 三种翻译模式：**
1. **行内模式（inline-only）**：仅高亮超出用户词汇水平的单词，点击显示 tooltip。最小 DOM 干扰，适合学习
2. **双语模式（bilingual）**：原文高亮 + 段落后插入译文行，原文与译文通过 data-index 交叉链接
3. **全文翻译（full-translate）**：段落后显示完整译文

**沉浸式翻译的翻译模式：**
- 双语对照（默认）：原文/译文逐段对照
- 仅译文：隐藏原文，仅显示译文
- 仅原文：恢复原始页面

**高亮系统差异：**
- notOnlyTranslator：基于用户词汇水平的智能高亮（只高亮"该用户不知道的词"）
- 沉浸式翻译：所有译文内容都显示（无词汇分级概念）

notOnlyTranslator 还支持 CEFR 词汇高亮——基于用户 CEFR 等级标记超纲词汇。

## 四、性能对比

### 4.1 翻译延迟分析

| 场景 | notOnlyTranslator | 沉浸式翻译 |
|------|------------------|-----------|
| 单句翻译 (LLM) | ~500-2000ms（含解析 JSON） | ~300-1500ms（流式输出） |
| 单句翻译 (传统API) | ~100-500ms | ~100-500ms |
| 页面批处理 | 后台批量翻译，分段缓存 | 页面加载时触发翻译 |
| 缓存命中 | < 1ms（内存） | < 1ms（内存） |
| 首屏加载影响 | 最小（仅扫描 DOM） | 较大（注入大量 CSS/JS） |

**notOnlyTranslator 性能优化：**
- EnhancedCacheManager: 双向链表 LRU + Chrome Storage 持久化
- TextComplexityAnalyzer: 智能路由减少不必要的 LLM 调用
- Parallel Translation: 传统 API + LLM 并行请求
- BatchTranslationManager: 防抖（150ms）+ 批量翻译（15段/批）
- ViewportObserver: IntersectionObserver 仅翻译视口内内容
- 渲染节流：每帧最多 10 个节点，最多 16ms（OptimizedHighlighter）
- 中文页面预检：lang 属性 + 内容采样（30% 阈值），跳过中文页面
- 本机词频过滤：跳过无难词的段落，节省 API 调用
- PerformanceMonitor: 全面的性能指标采集
- CostDashboard: API 调用成本追踪

## 六、代码架构对比

### 6.1 notOnlyTranslator 架构优势

1. **模块化程度高**：分层清晰（Background/Content/Popup/Options/Shared）
2. **扩展性设计**：通过 `TranslationApiService` 统一 API 格式，新增供应商只需添加配置

5. **状态管理**：Zustand + Chrome Storage 同步

### 6.2 沉浸式翻译架构优势

1. **PDF 引擎**：内置 PDF 解析和渲染引擎（建议 <100 页）
2. **视频字幕解析**：100+平台支持，含 YouTube 直播字幕（2026-03 新增）
3. **跨平台**：Chrome/Edge/Firefox/Safari + 移动端（iOS/Android） + Tampermonkey 用户脚本
4. **用户基数大**：300万 Chrome 用户、1000万+ 全球用户、Chrome 2024 年度最佳扩展
5. **输入框集成**：Deep DOM 集成，三连空格触发
6. **公司背景**：Funstory.ai Limited（香港），活跃开发（2026 年每月 3-4 个版本）

## 七、notOnlyTranslator 用户词汇系统架构

### 7.1 词汇量估算

**三级难度估算系统：**
1. **掌握度系统（最准确）**：每词掌握度 (0-1) + 置信度 (0-1) + CEFR 等级
2. **用户历史**：已认识(难度1) vs 已标记未知(难度10)
3. **词频管理器**：六级分层（常见词/CET-4/CET-6/TOEFL/IELTS/GRE），内建 JSON 词汇表 O(1) Set 查找

**贝叶斯更新（核心算法）：**
- 初始估算基于考试类型（CET-4: 4500, CET-6: 6000, TOEFL: 8000, IELTS: 7000, GRE: 12000）
- 用户标记单词时更新：根据词难度 + 标记结果，调整预估词汇量和置信度

### 7.2 掌握度系统 + SM-2 间隔重复

每个单词追踪的元数据：
- `masteryLevel` (0-1)：掌握度分数
- `confidence` (0-1)：估算置信度
- `knownCount` / `unknownCount`：标记历史
- `estimatedLevel`：A1-C2 CEFR 等级
- `nextReviewAt`：下次复习时间戳

**SM-2 算法：**
- 5 级评分制（ReviewQuality 枚举）
- 连对 4 次视为"已掌握"
- 难度因子最小值 1.3，默认 2.5
- 简单奖励倍数 1.3x
- 错误重置间隔 1 天

**对比沉浸式翻译：** 沉浸式翻译**完全没有**词汇学习体系。这是 notOnlyTranslator 的核心护城河。

### 8.2 模型选择建议

**性价比之王：** GPT-4o Mini（海外用户）/ DeepSeek Chat（国内用户）
- 延迟：~400-800ms 单句翻译
- 成本：约 $0.15/百万 token（GPT-4o Mini）/ ¥1/百万 token（DeepSeek）
- 翻译质量：4.2/5.0

**延迟优先：** Gemini 2.0 Flash / Groq(Llama 3.3 70B)
- 延迟：~200-500ms
- 适合需要实时反馈的场景

**质量优先：** GPT-4o / Claude 3.5 Sonnet
- 延迟：~800-2000ms
- 适合复杂学术/技术文本

**本地部署：** Qwen 2.5 7B（Ollama）
- 无网络延迟（0ms API 调用）
- 完全免费，无隐私问题
- 但质量略低于云端模型

### 8.3 Translation Extension 最佳实践

对浏览器翻译扩展，推荐以下分层策略：

```
用户默认 → GPT-4o Mini / DeepSeek Chat
    ↓ 失败
回退 → Gemini 2.0 Flash（备选）
    ↓ 再失败
最低保障 → DeepL / Google Translate（无需 LLM）
```

**关键考量：**
1. **TTFT < 300ms** 对用户体验至关重要（用户悬停等待翻译）
2. **流式输出** 对全文翻译场景价值大（沉浸式翻译的核心优势之一），notOnlyTranslator 当前不支持流式
3. **缓存策略** 比模型选择更能影响实际延迟
4. **批量请求合并** 比单条请求更有效率

## 十、结论

notOnlyTranslator 和沉浸式翻译是**差异化的产品**，而非直接竞品：
- 沉浸式翻译 = **通用翻译工具**，覆盖广、平台多、社区大
- notOnlyTranslator = **英语学习工具**，深度在自适应分级、学习追踪、词汇掌握

**核心建议：**
- 不需要在"多平台覆盖"和"PDF/视频"上正面竞争
- 应坚持"学习型翻译"差异化，把自适应词汇体系做到极致
- 需尽快补齐**流式输出**（对标沉浸式核心体验）
- LLM 模型推荐默认走 GPT-4o Mini（性价比最优）
- 放弃做"更大的翻译工具"，继续做"最懂学习的翻译器"
