# SUP-1362 竞品分析：NotOnlyTranslator vs 沉浸式翻译

> 分析日期：2026-05-14 | 分析师：CEO Agent
> 维度：代码架构、UI展示、交互设计、功能覆盖、翻译性能、LLM 模型选型

---

## 一、产品定位与差异化

| 维度 | NotOnlyTranslator | 沉浸式翻译 |
|------|-------------------|-----------|
| **核心定位** | 英语学习工具（按词汇水平选择性翻译） | 翻译工具（双语对照阅读） |
| **目标用户** | 英语学习者（CET-4/6/TOEFL/IELTS/GRE） | 需要跨语言阅读的所有用户 |
| **翻译粒度** | 单词/短语级别（仅超出用户水平的词） | 段落/整页级别 |
| **核心价值** | 个性化学习路径 + 贝叶斯词汇估算 | 即开即用的双语对照 |
| **开源状态** | 开源 | 已闭源（2023年1月起） |
| **平台覆盖** | Chrome/Edge 扩展 | Chrome/Edge/Firefox/Safari + iOS/Android |
| **用户规模** | 早期项目 | 10M+ 用户，Chrome 2024年度精选 |

**关键结论**：两者是**互补而非直接竞争**关系。沉浸式翻译解决"翻译一切"的需求，NotOnlyTranslator 解决"辅助学习"的需求。差异化壁垒在于词汇水平估算 + 选择性翻译能力。

## 二、代码架构对比

### 2.1 NotOnlyTranslator 架构

```
src/
├── background/          # Service Worker (MV3)
│   ├── index.ts         # 消息路由、上下文菜单
│   ├── translation.ts   # LLM API 调用（4层策略）
│   ├── translationApi.ts # 统一API调用服务
│   ├── hybridTranslation.ts  # 混合翻译（传统API + LLM）
│   ├── deeplTranslation.ts   # DeepL 优先翻译
│   ├── enhancedCache.ts      # 增强缓存（LRU + 段落级）
│   ├── storage.ts       # Chrome Storage 封装
│   ├── userLevel.ts     # 贝叶斯词汇估算
│   ├── textComplexityAnalyzer.ts  # 文本复杂度分析
│   └── llmEnhancedAnalysis.ts     # LLM 增强分析
├── content/             # Content Script
│   ├── index.ts         # 页面扫描、高亮注入
│   ├── highlighter.ts   # 文本高亮
│   ├── tooltip.ts       # 翻译Tooltip UI
│   └── marker.ts        # 单词标记
├── popup/               # 弹出面板（React）
├── options/             # 设置页面（React）
└── shared/              # 类型、常量、工具
    ├── types/index.ts   # 完整类型定义
    ├── constants/providers.ts  # 14个供应商配置
    ├── performance/     # 性能监控体系
    └── prompts/         # 翻译提示词版本管理
```

### 2.2 沉浸式翻译架构（外部观察）

- 闭源，无法深入分析
- 已知：Content Script 注入 + DOM 双语排版引擎
- 支持 PDF/ePub 内嵌渲染（非浏览器原生能力）
- 视频字幕需要独立的注入管道
- 20+ 翻译引擎集成

### 2.3 架构差异分析

| 维度 | NotOnlyTranslator | 沉浸式翻译 |
|------|-------------------|-----------|
| **消息架构** | Chrome Messaging（内容脚本 ↔ Background） | 未知，推测类似 |
| **缓存策略** | 段落级 LRU 缓存 + Chrome Local Storage（1000条目） | 推测类似，未开源 |
| **状态管理** | Zustand + Chrome Sync Storage | 未知 |
| **性能监控** | 完整体系（7类指标 + P50/P95/P99 + 告警） | 未知 |
| **翻译策略** | 4层降级：Hybrid → DeepL → Free Google → LLM | 多引擎切换 |
| **词汇分析** | 文本复杂度分析器 + 贝叶斯估算 | 无（不需要） |

**优势**：NotOnlyTranslator 有更完善的性能监控体系和多策略降级机制。

**劣势**：平台单一（仅 Chrome），无 PDF/文档翻译，无视频字幕支持。

## 四、交互设计对比

### 4.1 用户交互流程

| 交互场景 | NotOnlyTranslator | 沉浸式翻译 |
|----------|-------------------|-----------|
| **页面加载** | 自动扫描 → 高亮生词 | 手动触发整页翻译 |
| **点击生词** | Tooltip 显示翻译 → 标记已知/未知 | 显示完整翻译 |
| **标记生词** | 贝叶斯更新词汇等级 | 不支持 |
| **词汇量测试** | 内置测试 → 自动估算等级 | 不支持 |
| **复习系统** | SM-2 算法 + 闪卡 | 不支持 |
| **语境学习** | 上下文关联学习卡片 | 不支持 |

### 4.2 交互差异

**沉浸式翻译**：简单直接 → 打开即用 → 一键翻译 → 对照阅读
**NotOnlyTranslator**：学习闭环 → 测试等级 → 阅读标记 → 复习巩固

**关键差异**：NotOnlyTranslator 需要用户主动参与学习循环，沉浸式翻译是被动消费型工具。

## 六、翻译性能深度对比

### 6.1 NotOnlyTranslator 性能体系

```
性能监控架构：
├── API_RESPONSE_TIME     (警告: 2000ms, 严重: 5000ms)
├── DOM_RENDER_TIME       (警告: 100ms, 严重: 500ms)
├── STORAGE_OPERATION     (警告: 50ms, 严重: 200ms)
├── MEMORY_USAGE          (警告: 50MB, 严重: 100MB)
├── BATCH_TRANSLATION     (警告: 3000ms, 严重: 10000ms)
├── CACHE_OPERATION       (警告: 10ms, 严重: 50ms)
└── MESSAGE_LATENCY       (警告: 20ms, 严重: 100ms)
```

**4层翻译策略（自动降级）**：

```
策略1: HybridTranslationService（混合翻译）
  ├── 简单文本 → 传统API (DeepL/Google/有道)  → < 500ms
  └── 复杂文本 → LLM 增强分析                  → 1000-3000ms

策略2: DeepLTranslationService（DeepL优先）
  └── DeepL API → 高质量翻译                    → 200-800ms

策略3: Free Google Translate（免费回退）
  └── Web 端点 → 无API Key 场景                 → 100-500ms

策略4: Standard LLM（标准LLM）
  └── OpenAI/Anthropic/Gemini/...               → 500-3000ms
```

**缓存策略**：
- 段落级 LRU 缓存，最大 1000 条目
- Chrome Local Storage 持久化
- 缓存命中率统计 + 性能指标记录

### 6.2 沉浸式翻译性能（推测）

基于其产品形态推断：
- 整页翻译需要分块处理，推测批量 API 调用
- 多引擎支持意味着有引擎切换/降级机制
- Pro 版宣称"更快的响应速度"，推测有服务端优化
- 视频字幕需要实时性，推测有流式处理

### 6.3 性能对比分析

| 性能维度 | NotOnlyTranslator | 沉浸式翻译（推测） |
|----------|-------------------|-------------------|
| **首次翻译延迟** | 取决于策略：50-3000ms | 200-2000ms（传统API更快） |
| **缓存命中延迟** | < 10ms（本地存储） | 推测 < 50ms |
| **批量翻译吞吐** | 段落级并发 + 缓存 | 分块并发 |
| **内存占用** | 监控中（警告 50MB） | 未知 |
| **DOM 渲染** | 监控中（警告 100ms） | 优化较好（成熟产品） |
| **离线能力** | ❌（需网络调用API） | 部分（传统翻译API） |

**关键差异**：NotOnlyTranslator 的单词级翻译比整页翻译需要更多次的 LLM 调用（每个生词都需要独立翻译上下文），这对性能是更大挑战。

## 八、战略建议

### 8.1 短期行动（1-3个月）

1. **强化差异化壁垒**：沉浸式翻译不具备"学习闭环"能力，应重点投入
   - 优化贝叶斯估算算法
   - 丰富复习系统（增加题型、游戏化）
   - 完善语境学习

2. **性能优化优先**：
   - 单词级翻译的批量预加载（预测用户可能点击的词）
   - 缓存命中率优化（当前架构有改进空间）
   - 考虑引入 Gemini 2.0 Flash 作为低成本快速通道

3. **多模型智能路由**：
   - 当前已有混合翻译架构，可进一步扩展为"多模型路由"
   - 简单词 → 传统翻译/小模型，复杂句 → 大模型

### 8.2 中期规划（3-6个月）

1. **扩展平台**：Firefox/Safari 支持（沉浸式翻译覆盖的平台更广）
2. **PDF 翻译**：学习场景中 PDF 阅读需求很大（学术论文）
3. **术语库功能**：专业英语学习（医学、法律、计算机等）

### 8.3 长期愿景（6-12个月）

1. **AI 教师角色**：从"翻译工具"升级为"AI 英语教师"
2. **社交学习**：学习进度分享、词汇量排行
3. **内容推荐**：根据词汇水平推荐适合阅读的文章

## 九、总结

| 维度 | 结论 |
|------|------|
| **竞品威胁** | 低 — 定位不同，互补关系 |
| **差异化壁垒** | 高 — 词汇估算 + 学习闭环是沉浸式翻译不覆盖的领域 |
| **性能挑战** | 中 — 单词级翻译需要更多 API 调用，需优化缓存和预加载 |
| **模型选择** | GPT-4o-mini 综合最优，Gemini 2.0 Flash 成本最低，Claude 3.5 Haiku 质量最高 |
| **最大风险** | 沉浸式翻译如果加入"词汇学习"功能，会直接竞争 |
| **最佳策略** | 深耕学习场景，避免与沉浸式翻译在纯翻译功能上竞争 |
